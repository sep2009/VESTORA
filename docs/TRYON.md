# Virtual try-on (`/virtual-try-on`)

Three clearly different modes. A result is always shown with its own label and is never presented as another mode.

| Mode | What it is | What it is NOT | Available when |
|---|---|---|---|
| **Avatar preview** | The product as a generic garment shape, in the product's color, on a 3D mannequin you pick (the Outfit Studio avatar and garment preview; see `docs/OUTFIT_STUDIO.md`). | Not you, not the real cut or fit. | Always |
| **AI photo try-on** | An image generated by a third-party AI service from your photo and the product's catalog picture. | Not a fit prediction. | Only when a provider is configured **and** the product is supported |
| **3D garment preview** | The product's own 3D model (GLB/glTF) in the existing 360° viewer. | Not on a body or avatar. | Only for products that have a 3D model |

Every result sits next to the real catalog product (name, brand, live price and availability, color and size choice, a link to the product page and add-to-cart for the original product). No result tells the shopper what size to buy or claims the picture predicts fit. Copy avoids judging bodies.

## Honest failure states
- **No provider configured** (`TRYON_PROVIDER` empty): the photo tab shows "Not configured", explains what is needed, shows **no upload form**, and nothing is uploaded or faked. Avatar preview, 3D preview, product links and add-to-cart keep working. `POST /api/tryon/jobs` answers 503.
- `TRYON_PROVIDER` set to an id with no adapter → unavailable with that explanation. Credentials missing → unavailable.
- Product without a 3D model → 3D mode says so, explains that a GLB must be attached in the admin, and lists the products that do have one. No photo or avatar is shown instead.
- Product not supported for photo try-on (shoes, bags, accessories; no picture; demo product with a real provider) → disabled with the reason.

## Provider architecture (`src/server/tryon/`)
- `providers/provider.ts`: the contract (`TryOnProvider`: `submit`, `poll`, optional `delete`, `supports`, `retentionNote`). Everything provider-specific lives in one adapter file; components and routes never import a provider.
- `providers/index.ts`: registry, chosen **only** by `TRYON_PROVIDER`. It is **empty today**: no real provider is integrated and none of its API is guessed.
- `providers/test-provider.ts`: a development test provider (`TRYON_PROVIDER=test`; outside development needs `ALLOW_TEST_TRYON=1`). It exercises the whole pipeline without any AI and returns a hatched placeholder image that says "TEST OUTPUT NO AI USED". It never reads the photo. The UI labels it everywhere ("Test output · no AI"). Its behavior can be forced (succeed, fail, reject, unreachable, quota, slow) from the form for testing only.
- `jobs.ts`: validation, consent check, private storage, job tracking (queued → processing → succeeded/failed, progress 0–100, stage text), polling, retention sweeps, usage limits, owner-scoped access, deletion.
- Routes: `GET /api/tryon/config`, `POST|GET|DELETE /api/tryon/jobs`, `GET|PATCH|DELETE /api/tryon/jobs/[id]`, `GET /api/tryon/jobs/[id]/result`.

### Adding a real provider (when you pick one)
1. Read the provider's official documentation. Do not copy an API from memory. Settle: authentication, how to send a person image and a garment image (upload, URL or base64), supported garment categories and how they map to ours (`upper_body`, `lower_body`, `dress`, `outerwear`), asynchronous job or synchronous response, how to poll or receive a callback, result format and expiry, error codes, rate limits and pricing, data retention and training use of uploaded photos, region and data processing terms, and whether and how photos can be deleted.
2. Write `providers/<name>.ts` implementing `TryOnProvider`; map the provider's errors to `TryOnProviderError(code, message, retryable)`; fill `retentionNote` from the provider's own terms (it is shown to the shopper before consent); implement `delete` if the provider has a deletion API.
3. Register it in `providers/index.ts`, put its credentials in server-only environment variables, set `TRYON_PROVIDER=<name>`.
4. Have the provider's terms and the privacy policy reviewed (a photo of a person is personal data, and may be biometric data in some jurisdictions). Update `CONSENT_POINTS` and bump `CONSENT_VERSION` (every consent is recorded against the version and provider id; a stale version is refused).
5. Run `node scripts/e2e-tryon.mjs` with the provider's sandbox if it has one.

## Privacy and security design
- **Explicit consent**: unchecked by default, the file picker stays disabled until it is ticked, consent resets after each upload, and the server refuses any upload without the exact consent version for the configured provider. The terms shown say what is sent, to whom, how long it is kept and that the service has its own terms.
- **Validation**: type by bytes (JPEG, PNG, WebP only; no GIF/SVG/AVIF), 8 MB, 256–6000 px per side, ≤36 megapixels, checked in the browser for a quick message and again on the server.
- **Metadata**: EXIF/GPS, XMP, IPTC and text chunks are removed (JPEG, PNG, WebP) before anything is stored or sent. Pixels are not re-encoded.
- **Secure storage**: photos and results live only in the private `private_files` database table (never on disk, never in a public bucket, random names). No route serves a photo at all. Results are returned only by an authenticated route, to their owner (other users get 404), with `Cache-Control: private, no-store`, `nosniff`, `noindex` and a sandbox CSP.
- **Authentication and CSRF**: customer sign-in is required; state-changing calls need the CSRF header and a same-origin `Origin`.
- **Retention**: the photo is deleted as soon as the provider finishes or fails, and in any case after 60 minutes (a sweep runs on every call). Results are deleted after 24 h unless saved (30 days). Failed records disappear after 24 h. Orphaned files are removed. Interrupted jobs are failed and their photo removed.
- **Deletion**: delete one try-on (photo if still held, result, record, and a deletion request to the provider when its adapter supports it) or all of mine. The response says whether provider deletion was requested.
- **Usage limits**: 10 try-ons per customer per 24 h (failed attempts count, deleting history does not reset it), 2 at the same time, 20 upload requests per IP per hour (all adjustable by env).
- **Not logged**: photo bytes are never logged; the adapter contract says so.

## Tests run
- `node scripts/e2e-tryon.mjs` (74 checks, server with the test provider): provider config; image probing and metadata stripping for JPEG/PNG/WebP; anonymous, CSRF and cross-origin refusals; consent (missing, "no", stale version, wrong provider); photo validation (no photo, no/unknown product, unsupported product, text renamed .png, GIF, SVG, tiny, huge, truncated, over 8 MB) with nothing stored; a full job (progress monotonic, photo deleted when done, result served private/no-store/nosniff, expiry set); access control (other user 404 for job, result, delete, save; anonymous 401; path traversal; private files not web reachable); save/unsave; provider failures (generation failure, rejection, unreachable, quota) with clear errors, photo deleted, no result, retry; concurrency cap; retention sweep of an over-age photo; deleting a running job; delete one and delete all with files gone; daily limit.
- `UNCONFIGURED=1 BASE=<server without provider> node scripts/e2e-tryon.mjs` (4 checks): config unavailable, upload refused with a clear message and nothing stored, page says photo try-on is unavailable.
- Browser: avatar mode (selecting, replacing, removing, avatar choice, save, compare two saved previews side by side, add the original product to the cart with the right SKU and a size-required message, product link); 3D mode (viewer with a model, explanation for a product without one, picker filtered); photo mode (consent gating, invalid text file, too-small photo, valid photo preview, progress stages, result with test label, save, failure state and "try again", delete all); unavailable state on a server without a provider.

## Not done / limits
- **No real AI provider is integrated.** The AI photo path has only been run against the labelled test provider, which produces no try-on. Image quality, latency, cost, supported categories, retention and legal terms of a real service are unknown until one is chosen.
- Jobs run inside the web server process: one instance only. Scaling out needs a queue and shared storage (Supabase Storage or S3 with private buckets and signed URLs). Files are not encrypted at rest beyond filesystem permissions; use encrypted volumes or a provider KMS in production.
- Rate limits are in memory. There is no malware scan or face/pose check before sending a photo (a real service will reject unusable photos; the UI shows its message).
- Saved avatar previews are stored in this browser only; AI results are saved per account (up to 30 days). 3D previews cannot be saved or compared (only avatar and AI results can).
- Photo try-on needs a customer account. Demo products are only offered with the test provider (their catalog "photos" are drawings).
- Not tested: real phone camera uploads and HEIC (not accepted), screen readers on the 3D stage, a physical touch device.
